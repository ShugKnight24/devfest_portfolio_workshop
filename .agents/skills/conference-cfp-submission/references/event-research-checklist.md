# Event research checklist

What to extract before writing a single field, where to find it, and what each finding changes in the proposal.

## Hard constraints (from the CFP page and the submission form)

| Finding                                                | Where                                                | What it changes                                                |
| ------------------------------------------------------ | ---------------------------------------------------- | -------------------------------------------------------------- |
| Field list                                             | The form itself, or the CFP page's "what we ask for" | Which sections of the pack you produce                         |
| Character or word caps per field                       | Form hints, CFP page                                 | Draft length; count, never estimate                            |
| Formats and durations offered                          | CFP page                                             | Scope of the whole talk (see table below)                      |
| Submissions allowed per person                         | CFP page, often in the fine print                    | Whether the user should spread proposals across events instead |
| Speakers allowed per proposal, panel composition rules | CFP page                                             | Whether a co-speaker is possible at all                        |
| Deadline, notification date, event date                | CFP page                                             | Turnaround, and when to move the proposal elsewhere            |
| Anonymous or named review                              | CFP page, "review process" section                   | Whether the copy may name the speaker or employer              |
| Recycled-content rule                                  | CFP page or speaker terms                            | Whether a previously delivered talk is eligible                |
| AI-assistance policy                                   | CFP page or code of conduct                          | How much rewriting the user must do before submitting          |
| Travel, accommodation, ticket, honorarium              | Speaker terms page                                   | Whether the user can accept an acceptance                      |
| Recording and licensing terms                          | Speaker terms page                                   | Whether the employer must approve                              |

## Soft signals (from last year's schedule and the track list)

- **Track descriptions.** Copy the wording of the track you target; the proposal should echo its vocabulary, because chairs rank within a track.
- **What already ran.** Five to ten titles from the previous edition show the level, the house title style, and which angles are exhausted.
- **Who spoke.** A programme dominated by vendor talks or by end-user stories tells you which framing the committee rewards.
- **Stated wants.** Many CFPs say what they want more of: first-time speakers, end-user experience, non-tool-specific topics, novel approaches.
- **Mentorship and early-submission programmes.** Several events pair submitters with previous speakers or offer proposal review, and they gate it on submitting well before the deadline. Surface it to the user as soon as you find it.
- **Real proposals with their verdict.** speakerline.io publishes submitted proposals tagged Accepted or Rejected, each with its abstract and its reviewer-only pitch, indexed by speaker, event and tag. Read three accepted entries for the target event - or for the closest comparable event, since coverage skews to Ruby conferences - before drafting. Entries are self-submitted, so read them as house-style evidence, not as a representative sample.

## Format-to-scope mapping

| Format               | Typical length | Realistic scope                            | Notes                                                                                                                                      |
| -------------------- | -------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Lightning talk       | 5-10 min       | One idea, one takeaway                     | Widely treated as the easiest entry point, though no event publishes per-format acceptance data - say so rather than promising better odds |
| Standard session     | 25-30 min      | One problem, 2-3 takeaways                 | The default format, and the one most submissions target                                                                                    |
| Long session         | 45-60 min      | One extended case study with nuance        | Scarce; some events ask how you would cut it to the shorter slot                                                                           |
| Workshop or tutorial | 75-180 min     | Attendees build something                  | Prerequisites and environment setup must be explicit                                                                                       |
| Panel                | 25-45 min      | Discussion, no takeaway structure expected | All panellists usually named at submission; diversity rules may apply                                                                      |
| Poster or demo table | Varies         | One artefact, repeated conversations       | Rarely competitive; good for work in progress                                                                                              |

## When browsing is unavailable

Ask the user for exactly these, in one message:

1. The CFP page text, pasted.
2. Five accepted talk titles from the previous edition.
3. The track list with descriptions.
4. The submission form's field names and any caps shown next to them.

Anything still missing becomes an explicit assumption, listed at the top of the delivered pack, so the user can correct it before pasting into the form.
